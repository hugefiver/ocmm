# Deepwork roles on DSH 0.2

DSMM defines twelve unsuffixed normal roles: orchestrator, planner, plan-critic, builder, reviewer, oracle, oracle-2nd, creative, code-search, doc-search, clarifier and media-reader (each prefixed `dsmm-`). A role name is a persona and tool policy, not a model-selection claim. Reviewer is primary-model self-review; an Oracle is an external-model cross-check only when the caller explicitly selects a distinct model offered by the current DSH catalog. The second slot is priority order, not greater capability.

The DW display names introduced in the 0.1.3 source contract are `DW Orchestrator`, `DW Planner`, `DW Plan Critic`, `DW Builder`, `DW Reviewer`, `DW Oracle`, `DW Oracle 2nd`, `DW Creative`, `DW Code Search`, `DW Doc Search`, `DW Clarifier`, and `DW Media Reader`. Their native preset IDs, callable tool/provider identities and permissions are unchanged. Persona introductions use the DW role label while retaining the exact `dsmm-*` technical role ID; no display label is a callable-ID rename.

## Runtime surfaces

The 0.1.4 source contract distinguishes root eligibility from delegation enablement. Only enabled roles whose mode is `primary` or `all` are registered as native root presets: `dsmm-orchestrator`, `dsmm-builder`, and `dsmm-planner`, displayed as DW Orchestrator, DW Builder and DW Planner. If Builder is disabled in deployment configuration, only Orchestrator and Planner enter the root selector, and Builder has no child tool. Planner remains read-only; read-only access does not imply auxiliary-only status.

The nine auxiliary-only roles are `dsmm-plan-critic`, `dsmm-reviewer`, `dsmm-oracle`, `dsmm-oracle-2nd`, `dsmm-creative`, `dsmm-code-search`, `dsmm-doc-search`, `dsmm-clarifier`, and `dsmm-media-reader`. Enabled auxiliary roles remain native delegation tools; they are not broken or missing roots. Runtime profile selection never changes either inventory.

DSH 0.2's `agentPresets.register({ id, plugins })` is the native preset registry. When the host composes `agentPresets` (such as Web/Desktop), DSMM registers eligible roots as complete plugin compositions: persona, instructions, filesystem/search/web tools, seven bundled workflow skills, on-demand debugging, and role-specific subagent tools where appropriate. The native loading correction uses `persona.prefix` and `agent-instructions.maxBytes: 65536`; a directory or manifest alone cannot prove that the host successfully mounts the composition. Read-only compositions receive Agent-scoped native `tools.restrict({ deny: ['write', 'edit'] })`; shell tools are not composed into them. Orchestrator and Builder include native `@deepseek-ai/dsh-tool-subagent` instances whose `persona` and `toolFilter` actually shape each child. Read-only child filters allow repository reads/search, with web tools for doc/media roles; media image reading is available only when that tool exists in the host catalog. The provider must support persona, tool filtering and the host's depth/permission limits.

The DSH headless one-shot runner does **not** mount or select agent presets. When its startup bundle includes `@deepseek-ai/dsh-headless`, DSMM instead mounts the same role-specific subagent instances on each root Agent's tool plane. The tools remain schema-stable for DeepSeek Flash's addition-only tool catalog, but DSMM's monotonic guard rejects owned role-tool calls unless deepwork is active or a DSMM role preset is selected. Without configured role routing, native model inheritance and the DSMM opt-in boundary are unchanged.

`roleRouting` supplies role policies without adding dynamic model-selection permission. The aliased native provider derives defaults from its parent's admitted runtime snapshot, merges supported explicit native child options, and preflights the result through the parent's native `llm.resolveCallConfig` before native spawn; profile routes are not baked into standing preset/tool rows. For a trusted live, owned, zero-prefix one-shot child, the accepted explicit provider/model/effort survives through final request headers. Root, cold/unowned child and parent-seeded fork requests retain profile-primary resolution. Native spawn aliases retain trusted role identity in the child's durable descriptor, so two children inheriting the same parent preset can still have different routes and fallback chains. A missing or unknown child identity is not guessed from persona text, and a durable descriptor alone does not prove live ownership. DSH's standing `modelSelectionSettings` would re-register subagent tools in each child's own scope, bypassing its inherited-tool filter; DSMM therefore keeps it false. Changing a model never enables extra tools. DSH controls approval, sandbox, cancellation and child depth; DSMM never bypasses those controls. See [model routing](model-routing.md).

Only enabled root-eligible IDs are registered in the root selector. All enabled role IDs remain eligible for DSMM-owned materialized exports and role-specific child tools where the parent permits delegation. The canonical role has no suffix; no high/low/max suffix presets are generated by default. A separately authored native composition must preserve its canonical persona and restrictions, and is not a DSMM runtime file profile. Inspect the running tool schema or preset registry diagnostic rather than treating a file as callable proof.

## Optional static mirror

`agent-presets/` keeps twelve renderer-checked static role directories for inspection or native composition authors, **not** a directory scanned by the DSH 0.2 registry. Auxiliary templates do not become roots. The example deployment patch enables DSMM defaults only; it is not a scan-root declaration. `presets.materialize` defaults to false. If enabled, `presets.root` writes only DSMM-owned enabled role directories; adding that path to an obsolete `agent-presets.roots` config does not enable native discovery. In the source repository, regenerate snapshots with `node dsmm/scripts/generate-role-assets.mjs` after the TypeScript build; the development generator is not included in the published package.

Materialization keeps the role-bound `.dsmm-managed-preset` marker. Foreign, mismatched, malformed or linked directories/files are never claimed. A current marker with unexpected entries fails closed; only an exact legacy `managed by dsmm` directory with the three expected regular files is updated. Disabling an enabled role removes only its owned directory. No role becomes the host default by installing DSMM.

## Upgrade and evidence boundary

Older sessions selected directly into a now-auxiliary preset retain their history, but native cold resume may reject the removed root preset ID as unknown. This limitation must be disclosed before global rollout; DSMM must not silently substitute another persona or erase session history. See [compatibility](compatibility.md) for the upgrade procedure. Healthy Docker root audits, actual blank-session role selection with DW display names and read-only child denials are required for 0.1.4 acceptance; actual Desktop selector verification is a separate post-publication check.
