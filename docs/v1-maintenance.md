# v1 Skills and Prompts: Sources and Maintenance

This document describes the current source inventory, composition contracts, and maintenance rules. `v1` is the OpenCode configuration value and directory label; model-facing text calls the workflow `deepwork`. `prompts/codex/**` is a separate adapter surface.

## Final-State Contract

Documents, code and comments, tests, and commit messages state only concise final requirements, design, and behavior. Update intermediate text directly. Don't retain development histories, decision histories, rejected alternatives, or decision counterexamples. History is traced only through the Git commit tree. Strictly chronological roadmaps and changelogs are the only document exception; this maintenance document isn't a history archive.

`docs/superpowers/specs/` and `docs/superpowers/plans/` are only for final product requirements to be delivered. Each describes its final deliverable. Changed requirements use separate plans, not appended change histories. Non-product coordination and agent reports stay in conversation, not workspace plan/report/evidence files unless explicitly requested as deliverables, and never use those product directories. Routine non-product complexity does not itself require planner/critic work or a repository plan.

Tests protect valid requirements, functional behavior, and external interfaces against regressions. String, regex, snapshot, and parsed-content locks for documentation, commit messages, package information, and error/log wording without functional or system-boundary significance are prohibited. Verify executable configuration, protocol fields, and resource delivery through behavior. Deliverables require correct functionality, interfaces, and usability, not string/hash locks on all text files. Hashes/checksums are reserved for explicitly necessary integrity, provenance/security, or protocol identity; required release checks remain binding. Don't test decision counterexamples or assert that deleted components are absent. Update tests when requirements change; delete tests dedicated to removed modules, helpers, tools, or subsystems. Valid negative safety, protocol, and input-handling tests remain appropriate.

Tests must not freeze incidental files or lockfiles, build-tool details, descriptive package metadata, local OS/shell/path/PATH/CWD settings, dependency/runtime versions, or environment snapshots unrelated to product behavior or an explicit external or necessary delivery contract. Each test must expose a concrete requirement failure rather than preserve the current machine/tool setup. Behavior verifies configuration and delivery; whole-file string/hash equality and parsed incidental state aren't substitutes. Necessary integrity, provenance, security, and protocol pins remain valid for their concrete boundary. The automatically injected brainstorming skill and both GPT calibration sources carry this rule; prompt/document edits alone don't justify infrastructure/environment tests.

Git commits are the compatibility boundary. Uncommitted intermediate implementations may change incompatibly to meet final requirements without transition shims or tests preserving them. Existing committed contracts remain binding even when their files have uncommitted edits. Public API/protocol, security, data, permission, and irreversible-operation changes still need their applicable authorization. This rule doesn't authorize any Git write.

Current constraints, authorization boundaries, unresolved risks, and observed evidence remain part of conversation coordination and reports. Keep short-lived state in session and synchronize useful results at delivery or major phase boundaries, not every checklist update. Temporary, debug, disposable, or retired artifacts need no repeated stability/hash comparisons, correct status record at every instant, or completion write before deleting a finished disposable checklist/journal. Don't introduce repository debug journals or extra ledgers. Cleanup still requires exact task ownership, safe resolved paths, PID plus start identity, and preservation of user edits; lightweight temporary-state handling never weakens authorization, API contracts, or data guarantees. Final-state discipline must not conceal incomplete verification or defects.

## Source Inventory and Composition

Each adapter has nine deepwork sources: `default`, `gpt`, `claude-opus-5`, `gemini`, `glm`, `codex`, `planner`, `kimi-k27`, and `swe-2`. Each has five functional-role sources and eleven category sources. Ten categories are enabled by default; `cross-cutting` requires explicit user configuration.

Composition is role-first. The role prompt and applicable skills define scope, permissions, and output; model calibration is subordinate inside the composer-owned `<workflow-model-calibration>` envelope. `deepwork/gpt.md`, titled `GPT EXECUTION CALIBRATION`, is the shared GPT/Codex-family behavioral layer. It carries the zero-tolerance process-suppression section, which defines hash locking, repeat verification, ceremony tests, gate inflation, and over-asking as prohibited categories that must be aborted on trigger, with produced artifacts discarded and the suppression reported; hashes stay reserved for explicit external integrity, release, security, or protocol requirements. It also carries the goal-locked execution contract: work stays on the final requested outcome, and out-of-scope problems are recorded in one line and handed off for separate scheduling rather than absorbing the run. The execution categories (`coding`, `normal-task`, `complex`, `deep`, `quick`) and the orchestrator role carry the matching out-of-scope-finding contract: workers record such findings and finish their assignment first, and the orchestrator schedules recorded findings as separate work instead of expanding the current task or blocking integration. OpenCode adds the GPT layer once for the final detected model, including planning and category roles. `deepwork/planner.md` supplies plan-only doctrine, not a model generation. `deepwork/codex.md` supplies host-tool compatibility.

Codex profiles carry the shared GPT layer ahead of runtime model selection. Non-GPT models ignore GPT-specific behavior while retaining their role, embedded skills, planner doctrine, and adapter-tool rules. Opus 5/5.5 calibration is orchestrator-only and guarded by exact family detection. Kimi K2.7/K2.8 Preview/Code aliases and SWE-2 have separate guarded additive layers; these don't redefine reasoning-family classification or user configuration priority. Category sources contain generic role policy, not copied GPT calibration.

Workflow economy is owned by the orchestrator role. `agents/orchestrator.md` carries the authoritative policy: scale the pipeline to the request instead of defaulting upward, execute simple or clearly non-software work directly without planner, plan-critic, review, or a full suite, size verification to the changed area with no test run needed for a re-read-verified trivial adjustment, reference content by path, commit, or uncommitted working-tree change instead of an invented hash, require no unneeded verification rounds or sign-off steps, build no scaffolding that pins unrelated files or environment state, and recheck only what the current step depends on when runtime or path state drifts. Complex product implementation still defaults to `planner` → `plan-critic` → implementation, and an explicit skip never crosses a protected boundary.

Model calibrations only remove the residual tendency to inflate process past that policy, in each family's own register. `deepwork/gpt.md` states each suppressed tendency as a GPT behavior it must abort on trigger. `default` keeps the shortest list under `Process Economy`, `gemini` under `NO INVENTED RITUALS` / `NO PIPELINE FOR SMALL WORK` / `NO LOCK SCAFFOLDING`, `glm` in its zero-tolerance list, and `claude-opus-5`, `kimi-k27`, `swe-2`, and `planner` in proportional short form. Both adapters carry the same text.

The deepwork activation banner appears in `default`, `glm`, `gpt`, and `gemini`; those four are the only variants that own a whole-model injection slot, so the banner reaches every runtime model exactly once. `claude-opus-5`, `kimi-k27`, and `swe-2` compose on top of `default` and inherit it, `planner` is a subagent that never addresses the user directly, and the Codex adapter carries the banner only under an explicit runtime-model guard because its calibrations load ahead of model selection.

Category sources are a separate injection domain from deepwork variants: `frontend.md` and the other categories compose the category role prompt plus model calibration, never a deepwork variant body. A category therefore cannot rely on workflow policy it does not receive; `frontend.md` states its own scope condition, applying the four-step design-system workflow to UI construction and limiting a small adjustment to the tokens the change touches. Absolute phrasing in a category or variant governs requested scope only and never mandates unrequested process the workflow policy leaves out.

OpenCode deepwork sources use one `<deepwork-mode>` envelope. Model-facing files under `prompts/v1/**` use `deepwork` rather than the path label. Every assembled built-in role and category receives the workflow-independent `prompts/shared/shell-safety.md` block once. It requires the active runtime shell, short inspectable commands, and fail-closed destructive cleanup of exact owned targets.

### Skill Injection and Discovery

`src/intent/skill-loader.ts` defines `V1_INJECTED_SKILLS = ["brainstorming"]` and six `V1_COMMAND_SKILLS`. Only brainstorming is automatically injected into the OpenCode system message. All six v1 skills are registered as slash commands; the other five load on demand. Brainstorming therefore carries the complete final-state, product-plan, valid-test, coordinated-verification/evidence-reuse, and compatibility/authorization contract without relying on a particular role or model calibration.

Shared top-level skills are discovered by `loadSharedSkills`, not added to v1 system injection. Codex embeds brainstorming in each generated agent's `developer_instructions` and copies packaged skills with adapter-specific tool/name conversion. On-demand references use names such as `deepwork-writing-plans` rather than OpenCode slash commands.

### Workflow Ownership

Complex implementation of product business logic or behavior defaults to the orchestrator-owned `planner` → `plan-critic` → implementation sequence. A skip for that work is limited to simple, low-risk, clearly bounded work or an explicit user request; state its applicable condition in conversation. Clear requirements or strong model capability don't exempt complex product implementation. Non-product routine operations, docs, maintenance, and release preparation use direct execution when resolvable, otherwise a material question or useful `complex`/specialist delegation, not automatic or repeated planner/critic/review cycles. Explicit process requirements and verification for concrete major safety risks remain binding. No skip expands security, data, public API/protocol, permission, or irreversible-action authorization.

Planner remains plan-only and doesn't dispatch its critic or implementation workers. Plan-critic stays read-only and reviews feasible delivery, required outcome states, dependencies, risks, and evidence. Substantive blockers need correction, evidence-based rebuttal, or escalation; optional improvements don't delay implementation. Re-review only materially affected conclusions, without fixed receipts, hashes, round counts, or unlimited approval loops.

Delegations express the goal, useful completion evidence, and material scope/ownership, permission, irreversible-operation, and protocol/integrity identity boundaries. Workers may discover corresponding resources within that scope; exhaustive file inventories, per-item revision/hash/receipt locks, and fixed report fields aren't required. Discovery never expands permissions. Workers return their current deliverable, actual touched files, evidence, and unresolved risks in conversation. Formal planning and acceptance remain orchestrator-owned. Utility leaves are `quick`, `code-search`, `explore`, `doc-search`, `research`, and `media-reader`; read-only roles exclude editing leaves. Local coordinator categories have only the specialist permissions their active contracts allow. Callable schemas and effective permissions, not generated files or plan recommendations, determine availability.

Reviewer is primary-model or primary-lane implementation self-review. Oracle slots are external-model cross-checks in configured priority order; explicit user configuration can remove model heterogeneity. Both review implemented diffs, not plans, architecture proposals, research answers, or root-cause debugging. Review accepts a working-tree/staged diff plus new files or an authorized committed range; workers don't commit merely to provide review input.

OpenCode background tasks depend on the current callable schema. Keep dependencies foreground, use host completion/error notifications rather than polling, and preserve returned `task_id` continuation semantics. Codex uses its own host tools and has no equivalent OpenCode background-session or `task_id` resume contract.

### Verification

Read covering tests before changes. Select targeted checks and real-surface evidence for plausible regressions. For multi-task or parallel work, workers run lightweight local checks relevant to their substantive changes and hand off changes, local evidence/results, and material risks or unverified coverage. The orchestrator coordinates integration and global verification, consolidating necessary heavy checks at task completion or important phase boundaries to minimize full-suite frequency. Planning, delegation, and review sources preserve this ownership rather than assigning full suites to every small task. Don't weaken valid checks just to get green; report incorrect existing tests as findings and change them only to match final valid requirements.

Passing evidence is reusable when it covers the current claim and no change materially affects tested behavior or interfaces; unchanged code needs no rerun absent a relevant change. Dependency/environment changes during long tasks and unrelated parallel code edits may coexist with valid evidence; assess concrete relevance rather than require a frozen workspace or environment. Never classify changes affecting tested behavior or interfaces as unrelated. Supplement only affected or missing evidence and report uncovered risks. Failed, stale, irrelevant, or acknowledgement-only results aren't passes. Safety/data/API/permission boundaries, required release checks, explicit user verification, and repository pre-commit typecheck/test/build gates remain binding.

## Adapter and Generation Rules

Codex source prompts map host tools to Codex equivalents such as `multi_agent_v1.spawn_agent`, `update_plan`, `apply_patch`, and the LSP MCP. `loadAdapterConfig` selects `workflow: "codex"` for packaging. `src/codex/plugin-generator.ts` owns the workflow skill, agent TOMLs, embedded brainstorming, copied skills, and compatibility envelope. Generic dispatch brief labels are optional guidance, not required protocol fields or report sections; callable schema, role, and identity constraints remain binding.

Generate `.codex/agents/`, `plugins/deepwork/`, and `.agents/plugins/marketplace.json` only through `pnpm run gen:codex-plugin`; never hand-edit them. Check target paths for existing changes before generation and return conflicts to the owner rather than overwriting them. Both generated profile copies and packaged skill/resource inventories must match current configuration.

Unsuffixed planner/plan-critic profiles are logical normal. Suffix profiles are generated only for explicitly configured canonical variants; files aren't callable-availability proof. Every tier retains canonical role permissions, and `plan-critic-low` retains its xhigh-equivalent floor. Reviewer/Oracle floors and explicit model configuration remain authoritative.

The project `.codex/ocmm.jsonc` supplies a local model-selection snapshot, not a generation-time dependency on a global user file. OpenCode runtime effort policy and Codex static effort mapping are separate contracts: exact GPT-6 Sol/Luna runtime `none` is supported, Astra clamps it to `low`, and these families map runtime `minimal` to `low`; Codex static `minimal` maps to `high` and `none` isn't an allowed static effort. Review/plan-review floors still apply.

Source-to-generated consistency is checked by the normal generation command and diff/freshness gate, not by tests locking real policy prose. Generator text transport/conversion uses synthetic payloads; actual bundle checks verify executable fields, paths, resource delivery, and configured inventory. Release generation checks remain required.

## Maintenance Rules

1. Any change under `skills/v1/**` or `prompts/v1/**` updates this document in the same authorized commit, and changes to this document stay synchronized with the relevant source. Neither direction permits a history-only append.
2. Adding, deleting, or renaming a source updates its current mapping and relevant loader references. Skill frontmatter remains at the start for native loading.
3. Upstream syncs replace current source/version attribution and current local contracts directly. Preserve required license and notice material; don't accumulate dates, rejected imports, or synchronization receipts.
4. Compare authoritative upstream content with the local fork, preserve applicable local scope/permission contracts, and verify proportionately. Don't search reference-only checkouts or user directories outside the authorized project scope.
5. When source changes require bundle refresh, use only the generator and inspect actual assembled role/category/model paths, embedded brainstorming, and resource inventory. Report generation or runtime coverage that wasn't performed.
6. Don't add descriptive-text, negative-history, or Markdown-structure tests. A compile or source diff alone doesn't prove runtime composition or resource delivery.
7. Git authorization is operation-specific. Implementation isn't commit; commit isn't push, tag, rebase, or release. Don't create separate spec, plan, or maintenance commits by default.
