# ocmm 0.6.4 Release Design

**Status:** Approved

## Goal

Publish the current main-package changes as `ocmm` version `0.6.4` through the existing `v*` release lane after synchronizing the user documentation and passing all local release gates.

## Scope

This release includes the two local fast-routing feature commits already on `master` and the current documentation synchronization. It bumps only the main package from `0.6.3` to `0.6.4`.

The independent native LSP release remains pinned at `0.3.2`:

- `package.json.ocmm.lspVersion` remains `0.3.2`.
- `crates/ocmm-lsp/Cargo.toml` and `Cargo.lock` remain unchanged.
- No `ocmm-lsp-v0.3.3` tag or platform-package publication is created.

## Commit Structure

Use two commits:

1. A documentation commit containing the verified README and documentation corrections plus this design and the reviewed implementation plan.
2. `chore: bump version to 0.6.4`, containing every version source and generated Codex bundle change required by the release.

The second commit must keep the root version bump and generated Codex manifests together. This preserves the generated-bundle invariant enforced by `.github/workflows/release.yml`.

## Version Sources and Generated Artifacts

The release bump updates:

- `package.json.version` to `0.6.4`.
- `README.md` release examples to `VERSION=0.6.4`.
- `nix/packages/ocmm-unwrapped.nix` to `version = "0.6.4"`.
- `nix/packages/mk-ocmm-package.nix` fallback package name to `0.6.4`.
- `plugins/deepwork/.codex-plugin/plugin.json` and `plugins/deepwork/package.json` through `pnpm run gen:codex-plugin`.
- Any additional tracked Codex bundle file changed deterministically by the generator.

The marketplace and generated agent inventory are included only if the generator changes them. No schema, prompt, skill, Cargo, LSP package, or release-workflow source change is part of this release bump.

## Verification

Before any release tag is created:

1. Clear `OCMM_PROFILE`, `OCMM_NO_PROFILE`, and `OCMM_FAST` for local gates.
2. Run `pnpm run typecheck`.
3. Run `pnpm test`.
4. Run `pnpm run build`.
5. Run `pnpm run gen:codex-plugin` and prove the generated inventory is clean afterward.
6. Set `RELEASE_TAG=v0.6.4` and run `pnpm run check:release-version`.
7. Run `git diff --check`, sensitive-data scans, version consistency checks, and staged-scope checks.

If an active user `oc.exe` process locks the root native artifact, do not terminate it. Reproduce the same TypeScript and LSP build stages in an isolated working-tree copy, smoke-test the generated LSP wrapper, record the root build as blocked by the live lock, and clean all temporary artifacts.

## Publication

After both commits and all gates pass:

1. Re-query `origin` and confirm `refs/tags/v0.6.4` is absent.
2. Push `master` to `origin` without force.
3. Create annotated tag `v0.6.4` at the verified release commit.
4. Push only `refs/tags/v0.6.4`.

The tag activates the main `ocmm` lane. It must publish the npm package, GitHub Packages package, OpenCode and Codex release tarballs, checksums, and the GitHub Release while downloading the already-published `ocmm-lsp-v0.3.2` assets.

## Monitoring and Acceptance

Because `gh` is unavailable, monitor the release with the GitHub REST API. Completion requires:

- the `release.yml` run for tag `v0.6.4` to finish with `conclusion: success`;
- GitHub Release `v0.6.4` to exist;
- release assets `ocmm-opencode-plugin-0.6.4.tgz`, `deepwork-codex-plugin-0.6.4.tgz`, and `SHA256SUMS.txt` to exist;
- npm registry package `ocmm@0.6.4` to be visible.

## Failure Handling

- A pre-tag verification failure stops publication. Fix the cause and rerun affected gates before creating the tag.
- A rejected non-fast-forward `master` push stops publication; fetch and reconcile without force-pushing.
- A tag-push failure is retried only after confirming the remote tag is still absent and the local tag points to the verified release commit.
- A workflow failure after the tag is published is never repaired by moving or force-updating `v0.6.4`. Diagnose the failed run and use the repository's safe follow-up release process.
- Trusted Publishing, registry, or GitHub service failures are reported with the workflow URL and exact failed job; credentials are never printed.

## Non-Goals

- No LSP version bump or `ocmm-lsp-v*` release.
- No feature, schema, prompt, skill, workflow, or dependency changes.
- No force-push, tag rewrite, installation, or termination of active user processes.
