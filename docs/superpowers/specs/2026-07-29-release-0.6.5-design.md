# ocmm 0.6.5 Release Design

## Status

Approved by self-review. This document is the release authority for `0.6.5`; implementation and publication must follow its gates in order.

## Context

The user intent is: “继续工作，所有工作完成之后对上一个版本以来的所有修改进行一个review然后再发版”. The release therefore covers every product change from `v0.6.4` through the final release candidate, not only the current dirty worktree.

At design time, `master` is `12bd1e24bdfba3e364981481127eba382b9c3a43`, `origin/master` is `3f7daff0e5b435e36ca47bad1870ca76decd57bf`, and the latest tag is `v0.6.4`. Neither local nor remote `v0.6.5` exists at this point; that absence must be checked again immediately before publication. The main package is `0.6.4`, generated Codex manifests are `0.6.4`, and `package.json.ocmm.lspVersion` is `0.3.2`.

Projects 1 to 3 are in the local commit `12bd1e24bdfba3e364981481127eba382b9c3a43`. Projects 4 and 5 are an unstaged, uncached set of exactly 61 pre-existing paths. Their recorded project-5 artifact identity is `sha256:d25390601841a8202c3def91a3de58d6869f707a910f0a3dffcec51c2e8cb78a`. Their targeted tests, TypeScript typecheck, full TypeScript test suite, 35 Rust tests, TypeScript build, two generator passes, isolated OpenCode checks, and isolated Codex checks have passed. Oracle and Reviewer approved both projects.

The only known obstacle to a true root `pnpm run build` is five running `dist/bin/ocmm-lsp-x86_64-pc-windows-msvc.exe` processes that hold a native output lock. They are user processes and must not be terminated.

## Goals and Non-Goals

### Goals

1. Produce a clean, committed, review-approved release candidate that contains projects 1 to 5, the native staging correction, this release documentation, the release plan, the version bump, and deterministic generated artifacts.
2. Publish main package version `0.6.5` through the existing `v*` GitHub Actions lane.
3. Keep the independently released native LSP at `0.3.2`.
4. Review the entire committed range `v0.6.4..HEAD` with identity-bound Oracle and primary Reviewer receipts before any push or tag.
5. Install the released Codex plugin only from a checksum-verified GitHub Release asset into a durable, versioned local path.

### Non-Goals

- No LSP version bump, `ocmm-lsp-v*` tag, or platform-package release.
- No schema, lockfile, dependency, release-workflow, or unrelated cleanup change.
- No `gh` installation or use. GitHub public REST endpoints are queried with `curl.exe`; Git refs use `git ls-remote`.
- No direct npm publish, force push, tag overwrite, rebase, amend, reset, stash, or termination of user processes.
- No local OpenCode installation and no use of the source checkout or temporary extraction as the installed Codex plugin source.

## Approaches Considered

### A. Terminate the five locking LSP processes and build

Rejected. Those processes may belong to an active user session. Releasing must not trade a local build convenience for user-process termination.

### B. Accept isolated-build evidence as the final root build gate

Rejected. Isolated evidence proves compilation and packaging mechanics, but it does not prove that the actual release worktree can complete its root build. A release needs a true root `pnpm run build` pass.

### C. Avoid rewriting an already-identical native output, selected

The build becomes lock-safe only when the expected staged target already has exactly the bytes produced by the fresh Cargo binary. A byte-identical target is left untouched, preserving its content and modification time. A missing, different, unreadable, or stale target is still removed and copied as today, so a lock on a different file remains a hard failure. This is the smallest correction that permits a real root build without weakening its meaning.

## Lock-Safe Native Staging Architecture

Add `scripts/stage-ocmm-lsp-binaries.ts` as a small build-only helper and make `scripts/build-ocmm-lsp.ts` call it after Cargo produces the fresh binary. The helper owns staging behavior; the Cargo build script continues to own target selection and build orchestration.

For each expected `ocmm-lsp*` output name, the helper must:

1. Remove names matching the staging family that are not expected outputs.
2. Read the fresh Cargo source bytes and the existing target bytes when the target exists.
3. Preserve the target without opening it for rewrite only when the two byte sequences are identical.
4. Otherwise remove the target, copy the fresh source, and on non-Windows apply the executable mode.

The comparison is content-based, not size-based. It must not suppress errors for a different locked target. Unexpected-file cleanup remains mandatory so stale platform binaries cannot enter a release asset.

Add `src/shared/stage-ocmm-lsp-binaries.test.ts`, which is included by the `src/**/*.test.ts` test glob. Its cases must establish that an identical target retains both content and modification time, missing and different targets are copied, unexpected staged names are removed, and a rewrite failure is propagated instead of treated as success.

The decisive real-world proof is a root `pnpm run build` pass while the known locked binary is byte-identical to its fresh Cargo output. A deliberately different locked target must still fail rather than being silently accepted.

## Release Candidate and Commit Architecture

The candidate is assembled by ordinary additive commits only. Before each commit, inspect status, diff, staged scope, `git diff --check`, and a sensitive-data scan; then run the gates affected by the staged change. Do not use history-rewriting commands or unrelated cleanup.

1. Commit the exact current project-4 and project-5 61-path worktree as `feat: sync prompt and review workflows`. The overlapping source, maintenance records, tests, docs, plans, specs, and generated files form one coherent feature group.
2. Commit the staging helper, its caller change, and its test as `fix: avoid rewriting unchanged LSP binaries`. Record targeted tests, full relevant gates, and the successful true root build.
3. Commit this design and the later implementation plan together as `docs: plan 0.6.5 release`.
4. Commit the main version and deterministic generated outputs as `chore: bump version to 0.6.5`.

The user has authorized these release-scoped local commits, the normal `master` push, the annotated tag, and the tag push. Each irreversible action still requires the precondition checks in this document immediately before it occurs.

The version commit keeps the root version and generated Codex bundle in the same atomic commit, satisfying the release workflow's freshness check.

## Final Review Identity and Data Flow

The final review begins only after all four commits exist and the worktree is clean. It covers these requirements and implementation references:

- Projects 1 to 3: `2026-07-28-config-merge-prototype-hardening`, `2026-07-28-idle-continuation-fencing`, and `2026-07-28-model-chain-opus5-calibration`, with their matching design and plan files.
- Project 4: `2026-07-29-prompt-skill-upstream-sync-design.md` and `2026-07-29-prompt-skill-upstream-sync.md`.
- Project 5: `2026-07-29-review-artifact-identity-design.md` and `2026-07-29-review-artifact-identity.md`.
- This release design and its later release plan.
- The staging-helper correction and version/generated artifact commit.

Create one committed-range packet in an approved OS temporary directory. Its identity is:

```text
ARTIFACT_KIND=committed-range
BASE_SHA=<full output of git rev-parse v0.6.4^{commit}>
HEAD_SHA=<full output of git rev-parse HEAD>
```

Capture `git diff --binary v0.6.4..HEAD` as the review input, hash that artifact with SHA-256, and write an evidence manifest stamped with the same base and head pair. The packet also names the requirements above, the complete verification evidence, and all global constraints. It contains no credentials or raw sensitive logs.

Send the same packet to the highest available configured Oracle and the primary Reviewer. The currently callable schema supplies only unsuffixed `oracle` and `reviewer`, so use those roles rather than inventing a suffixed tier. Each receipt must bind its role/profile lane, task ID or session receipt, exact artifact identity, verdict, and report source.

The parent recomputes the full base and head pair after each lane returns. A missing field, a changed pair, or a finding blocks acceptance. Verify each finding; when a correction is warranted, commit it as a new commit, rerun only evidence affected by that correction plus the required final pass, rebuild the packet at the new head, and continue within the same reviewer task IDs. Both final approvals must bind the same current base and head pair. Delete temporary packet material only after the parent has recomputed the pair and recorded both current receipts.

## Test and QA Gates

Before the review packet is created, the clean candidate must pass the following checks in this order when their inputs are available:

1. Targeted staging-helper tests, including the lock-safe and mismatch cases.
2. `pnpm run typecheck`.
3. `pnpm test`, including all TypeScript and Rust tests.
4. `pnpm run build`, with a true root pass. The five known user processes remain untouched.
5. `pnpm run build:ts`, then two `pnpm run gen:codex-plugin` passes with a clean second pass.
6. `RELEASE_TAG=v0.6.5` and `pnpm run check:release-version`.
7. Root and generated-plugin `ocmm-lsp.js mcp` probes, each reporting exactly the eight supported LSP tools.
8. Isolated OpenCode registry and prompt checks, plus an isolated Codex package-install smoke check where the resulting package root, manifests, and wrappers are inspected without changing the user's live configuration.
9. Final status, scope, secret, version-consistency, generated-freshness, and `git diff --check` checks.

Any failed gate stops the sequence. Fix only the responsible cause, commit the correction normally, and regenerate review identity and evidence. The final packet uses evidence from the current candidate only; earlier evidence is not relabeled.

## Publish State Machine and Failure Handling

### Preconditions

Immediately before publication, verify a clean worktree, `master` checkout, exact reviewed `HEAD`, and current dual review receipts. Query `origin/master` and require either the recorded old value `3f7daff0e5b435e36ca47bad1870ca76decd57bf` or a value with the required exact ancestry after an intentional reconciliation. Confirm that local and remote `v0.6.5` are absent, and that `npm view ocmm@0.6.5 version` has no published version. Check the tag's peeled object when it later exists.

### Transition sequence

1. Push `master` normally, without force, then verify `origin/master` resolves to the reviewed `HEAD`.
2. Create annotated tag `v0.6.5` at that exact head with message `ocmm 0.6.5`.
3. Push only that exact tag. Never move or overwrite it.
4. Use `curl.exe` against GitHub's public REST API to identify the single workflow run for the tag, head SHA, and returned run ID. Poll with increasing backoff rather than rapid unchanged polling.
5. Require the run and its relevant jobs to conclude successfully.
6. Require GitHub Release `v0.6.5` to be final, non-draft, and non-prerelease, with nonempty assets named `ocmm-opencode-plugin-0.6.5.tgz`, `deepwork-codex-plugin-0.6.5.tgz`, and `SHA256SUMS.txt`.
7. Verify `ocmm@0.6.5` is visible in npm and that the remote annotated tag peels to the reviewed `HEAD`.

The existing release lane is the authority for npm, GitHub Packages, release assets, checksums, and GitHub Release creation. It verifies tag and package versions, runs typecheck, tests, TypeScript build, generated-bundle freshness, and downloads the pinned `ocmm-lsp-v0.3.2` assets before package staging.

If a pre-tag check fails, stop before publication. If the normal branch push is rejected, fetch and reconcile without force. If the tag push fails, retry only after proving the remote tag is still absent and the local tag still points at the reviewed head. If any publication step fails after the tag exists, never move the tag. Report the immutable partial state with the tag, peeled SHA, workflow run URL and job state, release state and assets, package visibility, and exact next safe repair path. Do not print credentials.

## Local Codex Installation and Rollback

Perform local installation only after the release state machine has succeeded. Download `deepwork-codex-plugin-0.6.5.tgz` and `SHA256SUMS.txt` with `curl.exe` into an approved OS temporary directory. Parse the checksum manifest and verify the archive's SHA-256 before changing any Codex marketplace or plugin state. Inspect the archive before extraction: it must contain the marketplace and plugin manifests, runtime wrappers, and native binaries required by the release package.

Extract it to the durable source path `%LOCALAPPDATA%\ocmm\codex-plugins\deepwork\0.6.5`. The directory is versioned and retained after future upgrades. It is not the repository checkout and it is not a temporary directory.

Capture `codex plugin list --json` and current marketplace state before a mutation. Then remove the existing Deepwork plugin and `deepwork-local` marketplace, add the durable package root as the marketplace source, and install `deepwork@deepwork-local` with the confirmed Codex `plugin marketplace` and `plugin add` commands. The command JSON must report an `installedPath` in Codex's cache, while the marketplace source reports the durable `0.6.5` path.

Verify all of the following before considering installation complete:

- `codex plugin list --json` reports Deepwork `0.6.5` and enabled.
- The installed manifest is version `0.6.5`.
- Hashes of the durable release extraction and installed cache payload correspond to the checksum-verified release content.
- Both installed wrapper locations report exactly the eight LSP MCP tools.

If switching fails, remove only the partial new plugin and marketplace state, restore the captured repository-root `deepwork-local` marketplace and its prior plugin installation, and report the failure. Do not remove an old durable version. Clean the download temporary directory after successful verification or completed rollback, while preserving the durable package source.

## Acceptance Criteria

1. Exactly the intended release commits form a clean `v0.6.4..HEAD` candidate, with no history rewrite or unrelated change.
2. The staging helper skips only byte-identical target rewrites, preserves identical-target modification time, cleans unexpected outputs, and propagates mismatched locked-target failures.
3. A real root `pnpm run build` passes without terminating the five user LSP processes.
4. Main version sources are `0.6.5`, LSP remains `0.3.2`, and generated Codex outputs are produced by the generator and fresh on its second pass.
5. Every listed local gate, wrapper probe, isolated surface check, scope check, sensitive-data check, and version check passes on the final candidate.
6. Oracle and Reviewer approve the exact same committed-range base and head pair, and their receipts contain all required identity fields.
7. `master` and the immutable annotated `v0.6.5` tag point to the reviewed candidate; the matching release workflow succeeds.
8. The final GitHub Release has the three exact nonempty assets, npm exposes `ocmm@0.6.5`, and the tag peels to the reviewed head.
9. The installed Codex plugin originates from a checksum-verified release archive at the durable versioned path, reports `0.6.5` enabled, and exposes the exact eight MCP tools.
