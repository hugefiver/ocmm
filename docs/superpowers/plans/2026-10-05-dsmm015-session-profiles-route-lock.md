# DSMM 0.1.5: structured profiles, session selection and independent route strategies

## Approved outcome and boundaries

Extend **DSMM**, not the root ocmm product, so a user can edit named runtime profiles with native provider/model/exact-effort controls and ordered role fallback rows, switch the profile of one session conveniently, and run simultaneous sessions independently. Preserve Deepwork/DW display names, stable `dsmm-*` role/tool IDs, canonical tools/skills/read-only restrictions, and native delegation/spawn.

The user's latest clarification is authoritative: these are **two distinct strategies selectable independently for each Agent role in each profile**:

- `startup-lock` (default): admit the primary or first admissible ordered fallback at Agent entry, unless explicit native user model-selection intent takes priority; keep that route until an authorized human selection/profile boundary, including bounded same-route `RATE_LIMIT` retries. Later generic failures do not automatically hop models/channels.
- `rate-limit-fallback`: begin with the same admission rules; after the configured number of rate-limit failures, advance the configured ordered role chain at a safe request boundary, with finite retry/switch limits. Different roles in one profile, and the same role in different profiles, may choose different strategies and retry parameters.

An optional profile-level default/inherit choice is useful, but never substitutes for the explicit per-role selector. A selected runtime profile remains an independent file outside plugin configuration. Native provider/account/auth configuration is not part of these files.

The separately authorized successor is `@dsmm/dsmm@0.1.5`, tag `dsmm-scoped-v0.1.5`. Root owns release/global/Desktop/real-model operations after proof; this plan authorizes no subagent git/global/release writes. Preserve immutable 0.1.4 and older tags, packages, artifacts, history and continuation controls. No API keys, copied accounts, logged-in browser state, ASAR patching, authentication bypass, global PATH/pnpm changes, or paid/rate-limit errors manufactured for testing. Keep DW background work off; no background task feature is in scope. Use pnpm within the existing pinned toolchains. Real Docker/native/UI evidence must precede publication; root typecheck/test/build precede any authorized commit.

## Rulings and minimal shared contracts

### 1. Normalize one role policy, not separate policy engines

Extend `DsmmRoleRoutingConfig`/the strict profile grammar with `strategy` and a nested per-role `rateLimit` policy, retaining existing `primary` / `fallbackRoutes`. Supply optional profile defaults under a single runtime-policy default block, then resolve a complete immutable role policy once. Recommended bounded fields are `maxRetries`, `initialDelayMs`, `maxDelayMs`, `maxTotalDelayMs`, `switchAfterRateLimits`, and `maxSwitches`; defaults are startup-lock, three same-route retries, 500 ms initial delay, 10 s single-delay cap, 30 s total delay cap, threshold three, and at most two switches. Limits should be strict finite integers (retry/threshold/switch caps no greater than 10, single delay no greater than 30 s, total delay no greater than 120 s). Do not silently turn malformed values into valid defaults. Exact names may follow local conventions, but the same resolved policy must feed UI/status/admission/recovery.

`maxRetries` counts requests after the first request on a route; `switchAfterRateLimits` counts **distinct completed native request attempts** rejected with RATE_LIMIT/429, including the first. Duplicate error delivery is not another attempt. In rate-limit-fallback, switch on the first safe failure that reaches the threshold; below threshold, retry only while the finite retry/delay budget permits it. If the retry budget runs out before threshold, stop visibly. Counts reset after an accepted successful request, or a new explicit admission/lock generation; switched routes start fresh finite same-route counters but consume the epoch's switch cap. Reaching chain/switch/delay exhaustion stops visibly, never wraps to primary. Deduplicate candidates by provider/model, preserving order and exact effort, so changing effort alone cannot buy extra retry opportunities.

The new strategies' RATE_LIMIT policy is their own explicit finite behavior, not an accidental consequence of legacy `runtimeRecovery.enabled`. Keep that legacy field parse-compatible for its existing generic/continuation concerns; do not silently reinterpret it as the new strategy selector. All omitted strategies resolve to safer startup-lock, including old documents. Old generic fallback chains stay loadable/editable but no longer imply later generic automatic hopping by omission. If legacy generic behavior must remain selectable, require a clearly named explicit advanced opt-in and keep it separate from the two user-facing strategy choices. Document the migration, effective policy and cost of the default change; test omission versus explicit empty role chain, unchanged baseline/deployment precedence and deliberate opt-in. No automatic rewrite of user drafts/config.

### 2. Admission versus availability

Absent explicit native user model-selection intent, Agent entry chooses the first **native-resolvable** configured candidate in order, or the inherited native route when no explicit primary exists. This is metadata/preparation admission, not a health check. Native catalog listing is advisory, custom/manual IDs are not rejected merely because absent from listModels, and no sacrificial completion is sent. A session sidecar persists profile choice, not a permanent old-process route lock: every new native Agent/cold resume re-admits under the pinned profile and authoritative native user intent, with a fresh ephemeral entry lock generation owned by C.

Strict validation still rejects malformed/unsupported exact efforts and policy fields. Profile Apply must not reject a usable ordered policy merely because a dormant alternative cannot currently resolve: structural errors remain hard errors; classify route availability separately, accept when at least one candidate is admissible, and expose unavailable candidates accurately. If no Agent-native LLM service exists, report the actual validation limitation rather than fabricate availability. The request/alias preflight is authoritative before native prepareCall.

An exact recognized unavailable route failure on the **first actual request**, before any provider output, message/tool fragment or tool execution was accepted, may advance the remaining bounded ordered candidates. Start with narrow native `NO_ADAPTER` / native exact model-not-found semantics; add other exact adapter-proven unavailable codes only with reproduction evidence. `RATE_LIMIT` never counts as unavailable and retains the selected route in startup-lock even on the first request. AUTH, missing/invalid credentials, quota/payment, context overflow, invalid arguments, cancellation, ambiguous transport/server failures and message text never authorize startup hopping by inference. Once any output/tool evidence exists, or after startup settles, generic errors default to the native failure outcome. If the native contract cannot prove pre-output/no-replay, refuse the switch.

**Every DSMM automatic retry requires a positively proven no-output native attempt**, including startup-lock's same-route RATE_LIMIT retry, backoff retry, startup candidate advance, explicit legacy automatic recovery and rate-limit-fallback rollover. A route staying the same does not make replay safe. Rate-limit-fallback is a deliberate route-generation change, not prompt/tool replay. Preserve already accepted prior steps and the native tool loop; never synthesize a user message, restart a turn, resubmit completed tools, replace a persona or secretly retry a one-shot child.

The native `agent/request-error` payload has no output indicator and can fire after partial chunks. Correlate the exact native attempt ID plus turn/step and committed assistant/attempt settlement sequence/compact stream, or the public `agent/assistant-stream` attempt IDs/chunks/settlement signals (`dsh-agent/lib/types/runtime-types.d.ts:107`). Evidence must establish that this exact failed attempt accepted no text, reasoning, tool fragment, completed block or executed tool. Missing, ambiguous, mismatched, out-of-order or any partial/completed output evidence forbids **all** DSMM retry/switch scheduling. Stop the owned DSMM branch terminally without invoking/falling through to native `mode:always` or another downstream retry owner; clearing a pending fallback while allowing an unbounded host retry is not refusal. Keep native behavior outside the DSMM-owned branch unchanged. This fence is an implementation gate: if public attempt correlation cannot prove no output, fail closed rather than infer it from status/header/error alone.

### 3. Session selection and admission epoch

Keep global `.selection.json` as the default for future unscoped roots. Add separate session-choice sidecars under the trusted `profileContext.dir/dsmm-profiles` root, keyed by a SHA256 of the validated **native** session ID, not a caller path. A sidecar pins the exact native session ID, an immutable profile revision (or explicit deployment baseline), its own CAS revision, and a monotonic/unique admission epoch. The sidecar contains only bounded identifiers/policy provenance, never history, credentials, providers or native account configuration. Reuse the existing store's containment/no-link/single-lock/atomic replacement checks; no lock stealing or best-effort fallback to baseline on corrupt selection. Bound sidecar inventory and content, returning a visible refusal before commit when full. Admission from the global default uses the Host's already-admitted immutable selection, never an unvalidated reread of an externally changed pointer/draft.

Suggested additive backend shape:

```ts
describeSession(sessionId): Promise<SessionProfileSnapshot>
selectSession(sessionId, request): Promise<SessionProfileSnapshot>
// request carries its sessionId and existing profile/CAS fields;
// strict validation requires it to equal the separately validated sessionId.
```

`id:null` means explicitly pin deployment baseline for that session; absence of a sidecar retains old cold-resume/global-default behavior. Global describe/select keep their existing wire meaning. Session responses distinguish global default, committed session override, current admitted epoch, actual role route/strategy/retry state and whether a switch is presently allowed. Save/edit never activates either scope.

New scoped descriptors use strict JSON bounded stable `sessionId`/request parameters, deliberately not early Typert lookup parameters. Inside the RPC, validate exact `ctx.connection.operator === invocation.peer`, abort and the full strict JSON payload/same-ID guard **before** invoking genuine public `apiSession.resolveAgent(sessionId)` or the registered native agent provider's public `resolve`. The actual native descriptor vocabulary is `source:'lookup', key:'agent', wire:'agentId'` with native `SessionId` type symbol `@deepseek-ai/dsh-session/types#SessionId`, not `source:'agent'`; these early descriptors are inappropriate here because lookup can cold-resume before authority/full payload validation. No handcrafted DSMM cold loader/private read or unavailable-resolver fallback is authorized. Global methods retain their existing contract.

After authority-first native resolution, require the exact captured ordinary/root registry object, reject runtime-owned children and `session.header.origin === 'subagent'`, and use `runMaintenance` to reserve true idle immediately. Refuse busy/maintenance/disposed/not-owned targets; never wait indefinitely or silently queue a human change to some future turn. Recheck `agents.get(id) === capturedAgent` and admission epoch before/after async validation and inside the store's final pre-rename/CAS fence. Aborted/replaced Agents cannot commit/publish late state. Disk commit precedes complete in-memory publication with no intervening await. A failure retains old disk/in-memory admission. SDK RPC tests may use the actual native CredentialProvider with a fresh in-memory Map at its IO boundary for generated signing-key state only; no credential disk/user reads/login or authenticated-UI claim.

An explicit successful switch creates a new immutable root admission for subsequent requests/new children. Existing running requests are already excluded by the maintenance reservation; already-created children keep their captured old admission, even if they are idle. Do not recursively mutate descendants. Exact runtime `isOwnedBy` remains the only inheritance authority; durable lineage is not a live-owner claim. New children after the switch inherit the new epoch. On cold resume, load an existing session override during awaited creation before wakes; no override retains the documented prior global-current contract. Presets, skills/tools and persona remain native and unchanged. Clear/compact creates a new native session identity: do not infer transfer from lineage; inherit a still-live parent/owner only where native ownership proves it.

Use an internal immutable admission object `{settings, profile identity, epoch}` and a single `admission(agent)` accessor consumed by routing/recovery/status. Include persisted selection epoch, resolved strategy/retry policy and C's separate ephemeral Agent-entry lock generation in role-policy identity so pending reservations and old-process durable route folds cannot affect a new entry. Live Agents remain locked until explicit human selection/profile boundaries; cold resume must re-admit rather than reuse a previous process's fallback lock. Existing exact `dsmm/role-policy` payload retains its three-key grammar by hashing the new identity; no new DTO/event is needed for the entry generation. Accepted native request headers provide current-generation route provenance. Do not add new session events unless these existing facts prove insufficient; any necessary event extension then requires the full audited ignorable/persistence/repair/stock-reader regression chain, not only TypeScript declaration changes.

### 4. One RATE_LIMIT retry owner

Within a scoped DSMM role's new strategy, the native `agent/request-error` coordinator owns RATE_LIMIT admission/count/cap/switch and must not invoke a competing downstream retry handler first if that would schedule a second delay or allow native `always` to bypass the finite policy. Outside that branch, preserve exact host-first behavior and downstream identity. Keep all provider calls and step retry dispatch in the native loop; no parallel agent/task engine.

Use one fenced state per exact Agent/admission epoch/lock generation/native attempt ID and turn/step/settlement coordinates. Establish the universal no-output proof before consuming retry/switch budget or waiting, and recheck correlation/abort/epoch before returning the retry action. A one-shot pending route is applied by existing `agent/request` middleware after downstream native route selection and before final calibration; primary policy cannot overwrite it. Apply exact named effort; omission clears adapter-owned stale effort, preserving unrelated config. Reject late duplicate errors, stale policy/epoch, closed/superseded step, changed native header/provider, aborted signal and disposal. A retry remains on the same concrete admitted route unless the chosen explicit strategy authorizes a safe switch, but same-route retries still require the identical no-output fence.

If the optional native retry executor cannot accept a narrowed bounded policy through public hooks, a single abortable delay inside this existing error middleware is acceptable: sanitize/finite-bound `providerRetryAfterMs`, obey per-delay/total caps, cancel on abort/disposal, and never create an independent timer-driven request. Invalid Retry-After does not cause infinite waiting or immediate uncontrolled retry. Tests must prove operation both without native retry executor and with a native `mode:always` downstream handler, including zero budget, duplicate delivery, abort while waiting and exhausted budgets. Do not claim executor integration from catalog/types alone.
