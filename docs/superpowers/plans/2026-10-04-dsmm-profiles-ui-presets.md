## Three distinct concepts

| Concept | Owns | Required relationship |
| --- | --- | --- |
| DSH deployment profile, currently `desktop` | Native bundles, provider catalog, account/login, UI preferences, package management | Retain the native profile and its existing state. |

## Decisions and unresolved contracts

### Settled implementation direction

1. Add explicit role-mode metadata and one shared root-eligibility predicate. The settled source-parity policy is `primary OR all`: orchestrator, builder, planner are possible roots; the user's disabled builder means **orchestrator and planner only** in the system selector. Do not use `access: read-only` as a synonym for subagent: root-capable planner is read-only. Specialist enablement and root selector exposure are separate inventories.
2. Independent files are the authoritative profile contents. DSMM plugin configuration contains no default profile definitions. Writable drafts are `<root>/<id>.jsonc`; explicit selection creates/reuses an immutable `<root>/.revisions/<hash>.jsonc` and atomically writes a minimal `.selection.json` with version, ID, and revision. Saving a draft never changes the active revision or rewrites `cordis.patch.yml`.
3. External profiles contain runtime-only DSMM settings from the exact allowlist below. Roles, skills, mode naming, prompt/composition controls, preset materialization, LSP/processes, native providers/accounts, and installation remain deployment-only; reject them with actionable explanations. A route can reference an existing native provider/model; it cannot introduce its credential or bypass advertised effort validation. Native root/auxiliary composition and role-provider universe do not change when selecting a profile.
4. Parse and validate files before activation or persistence, with bounded sizes and structured nonsecret diagnostics. Distinguish absent routing/fallback keys from explicit empty values. Use the existing settings resolver as the semantic authority rather than a second divergent normalizer.
5. Selecting a profile affects **newly created Agents only**. Every existing Agent, including a blank one, keeps its admitted immutable runtime settings for this live Host; children inherit `request.parent`'s snapshot. There is no profile-driven blank-session update, canonical preset re-registration, synthetic lifecycle event, or durable historical per-session settings guarantee. After Host restart, cold resume admits the current selected settings, consistent with native composition behavior; UI warns explicitly.
6. Profile operations use a host service exposed through the **authenticated native UI RPC/extension surface**, not an unauthenticated HTTP endpoint, copied browser auth, a model-visible write tool, or arbitrary filesystem path parameters.
7. The package remains opt-in by default; preserve the user's explicit active mode, builder disable, nine role policies, native routes, exact effort distinctions, and host-owned cancellation/recovery permissions.

## Wave 2 — Independent-file profiles and safe revision management

Goal: profile discovery, read, edit, switch, and persistence work without config-object definitions, data loss, credential exposure, or mid-session policy mutation.

Suggested cohesive modules, names adjustable to verified repository/native contracts: `dsmm/src/profiles.ts` for parsing/resolution/revision descriptors, `profile-store.ts` for bounded safe IO, `profile-service.ts` for authenticated draft/selection operations, plus integration changes to `settings.ts`, `index.ts`, `dsh-types.ts`, and runtime consumers that need Agent-specific settings (`commands`, `mode`, `guards`, `model-routing`, `runtime-recovery`, provider/child routing, and `status`). Native preset/persona/tool/skill composition remains deployment-owned and is audited once after startup. Tests belong beside these seams under `dsmm/test/`.

Use one writable versioned JSONC draft per stable ID at `<profileContext.dir>/dsmm-profiles/<id>.jsonc`. Selected content is an immutable content-addressed file under `<root>/.revisions/<hash>.jsonc`; `.selection.json` contains only version, ID, and revision. Resolve `profileContext.dir` from the native service; a missing context is an explicit error, not a user-home fallback. JSONC allows user comments and matches the repository's file-profile convention, but the parser must be local/package-complete and cannot import root ocmm source. Use a strict filename ID grammar such as ASCII letters/digits/hyphen/underscore, with Windows reserved names and case-insensitive collisions rejected. Do not accept paths from RPC or treat `.selection.json`/`.revisions` as editable profile IDs.

The **exact runtime settings allowlist** is:

- `defaultActive`
- `roleRouting`
- `workflow`
- `deepseekV4ProCalibration`, `deepseekV4ProDefaultReasoningEffort`, `deepseekV4ProMaxReasoningPresets`
- `deepseekFlashCalibration`, `deepseekFlashDefaultReasoningEffort`, `deepseekFlashMaxReasoningPresets`
- `guards`
- `runtimeRecovery`

Keep existing nested semantic validation and finite bounds; distinguish absent fallback policies from explicit empty chains. Document fields and precedence. Reject `roles`, `skills`, `modeName`, `promptOrder`, `section`, `presets`, `lsp`, profile recursion, provider/account/auth/header/env, install, arbitrary Cordis rows, and unknown fields with a message identifying the field and directing structural changes to deployment configuration. Do not silently ignore them or expose arbitrary field editing as supported. A UI edit cannot weaken canonical readonly tool composition/filter restrictions even when a runtime guard setting changes.

Precedence: built-in DSMM defaults → existing deployment DSMM config → selected immutable runtime-only revision. Structural settings always come from deployment configuration. A missing selection means the unchanged deployment baseline, shown clearly in UI; installation creates no inline definitions or fake user profiles. Migration from 0.1.1 settings is explicit/reversible: UI can save supported runtime settings to a draft while preserving deployment roles, skills, account/provider/UI rows, and other structural config. Saving does not select it. Explicit selection reads and validates the draft, validates model routes/efforts against the available native scope/catalog, pins its exact bytes, and commits the pointer. Missing/invalid/linked draft or revision, invalid model/effort, or digest mismatch fails visibly and does not silently choose another route/profile.

Selection metadata is DSMM-owned, minimal, versioned, and separately persisted; it contains no copied profile object. UI edit requests carry profile ID and expected draft revision, and selection protects against a draft changed since inspection. Preserve comments by saving actual edited JSONC or document deliberate structural form behavior. Read-only discovery returns bounded summaries without credential-bearing config fields. The UI distinguishes draft revision, globally selected immutable revision for future Agents, and a receiving live Agent's admitted snapshot. Editing a selected profile draft leaves the selected revision unchanged until explicit selection.

Filesystem safety is a release requirement:

- Resolve the native root once, validate every parent/target is inside it, and reject symlink/junction/reparse traversal, nonregular targets, invalid IDs, reserved names, and case collisions. Verify again under the write lock; checking once before an async operation is insufficient.
- Use cross-process locking plus optimistic revision checks. Concurrent UI edits or external file edits produce a conflict, never a last-writer-wins overwrite. A lock timeout is a structured error; **do not steal stale-looking locks** or bypass the writer lock.
- Validate bounded candidate content before opening any overwrite path. Write a new same-directory exclusive temporary regular file, flush as supported, and atomically replace the exact target. Preserve the previous bytes on failure; on Windows, do not delete the old file first as a substitute for atomic replacement. Clean only task-owned temporary files.
- Profile switching serializes validation and pointer persistence, **not preset replacement**. Validate allowed runtime config and native model/effort semantics first, write/reuse an exclusive immutable content-addressed revision, then atomically replace `.selection.json`. Reusing a revision requires matching its digest and exact bytes; never overwrite a malformed/corrupt immutable file. Publish the prevalidated in-memory current snapshot only after pointer success. If pointer commit fails, the old selected pointer and current settings remain unchanged; an orphaned immutable revision is harmless and may be retained. New Agent admission reads one complete immutable current snapshot, never a partially applied settings object.
- Admit immutable runtime settings at root Agent creation. Every existing root, **including a blank root**, and its in-flight recovery stay on that admitted snapshot. Children inherit the exact `request.parent` snapshot. This retention is live-Host-only; after restart cold resume admits the current selected settings under native behavior. Do not append synthetic lifecycle events or promise durable historical per-session snapshots.
- Keep the deployment's role enablement/provider alias universe and native preset/tool/skill compositions invariant across profile selection. Do not bake per-profile child `agentOptions` into standing preset or headless role rows. At `provider.start`, derive role route from the admitted parent snapshot and use the parent's native `llm.resolveCallConfig` for preflight **before** native spawn. Preserve descriptor, role identity, readonly filter, persona, signal, finite recovery, and native cancellation. The aliased-provider native regression must demonstrate that configured route/effort survives this path without a parallel spawn implementation.
- Expose no profile management tools to models or delegated children. UI backend authorization must hold independently of omitted buttons. Saving/switching profiles cannot enable child write/delegation or dynamic `modelSelectionSettings`.

Acceptance: independent drafts and immutable selected revisions with digest/pointer validation; no inline profile objects; draft save does not activate; successful explicit selection changes only future-Agent settings; pointer failure retains old disk/current state; no stale-lock stealing; unchanged deployment structural/account/provider/UI sentinel state; rejected deployment-only/unknown fields with actionable diagnostics; traversal/link/reserved-name/digest rejection; concurrent draft edit conflict; no cross-profile Agent leakage; every existing root including blank retains its live snapshot and children/recovery inherit it; after a fresh Host process the current selected immutable revision is admitted even if its draft has changed; cold-resume behavior/warning matches native semantics rather than promising historical settings. Exact route/effort, explicit-empty fallback, native aliased-provider preflight, and readonly child behavior remain tested.
